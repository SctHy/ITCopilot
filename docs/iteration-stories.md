## 1. 多 Agent → 单 Agent：用评测决定删掉自己写的架构

**起点**：最初的设计是按领域拆成 5 个专职 Agent，由规划器分派，这也是当时很常见的做法。

**发现**：在 64 个分层场景上做配对比较。按意图路由到单个专职 Agent（single）40/64，规则规划器加多个专职 Agent 并行（bounded）44/64，作为对照的单个通用 Agent 63/64。

**定位**（逐条看失败）：
- single 的失败来自"路由即能力边界"：错误码、资产查询被分给了没有对应工具的 Agent。
- bounded 的失败来自规则规划器：漏掉领域，或者用户没要求也追加建单。

**改动**：先给多 Agent 一个公平的机会。改为 LLM 规划、只在用户要求时建单、按步骤数计算 token 预算。

**结果**：在 42 个重跑场景上，bounded 41/42、bounded_all 42/42、通用 Agent 40/42，三者没有显著差异；τ-bench 式多轮评测上两两之间 p ≥ 0.45。但多 Agent 的 token 多约 60%，三领域场景是通用 Agent 的 2–4 倍。

**决定**：v4.0 删掉规划器、5 个专职 Agent 和相关的状态机与配置。按领域隔离写工具原本是为了安全，这个作用已经由代码里的身份、策略与审批承担，不需要靠拆 Agent 来实现。

**边界**：结论只适用于当前的工具规模（7 个本地工具）。工具增加到几十个时需要重新评测。

**可能被追问**：为什么先修多 Agent 再删，而不是直接删？如果不先修好规划器，比较对多 Agent 不公平，结论就站不住。

## 2. 重复建单：最大的失败来源不在 Agent

**发现**：τ-bench 式多轮评测由 LLM 模拟用户，信息只在被问到时才透露，最后按员工的最终状态评分（权限集合、工单数量必须精确一致）。修复前 247 段对话失败 101 段，其中 73 段（72%）的失败原因相同：多出了工单。四种 Agent 策略都有这个问题。

**定位**：用户补充信息、说"确认提交"，或者要求"补充进工单"时，Agent 会重新调用 `create_ticket`，每次都生成一张新的待审批单。审批人逐张批准，就出现了重复工单。这是审批层缺少"同一件事"的概念，换哪种 Agent 架构都会遇到。

**改动**（`workflow/store.py::_supersede`，[ADR 0007](adr/0007-supersede-pending-approvals.md)）：同一会话、同一申请人的新审批，如果完全覆盖某张仍待审批的旧单（键是工具 + 员工，权限申请再加系统），旧单标记为 `superseded`，不能再被批准，替代关系写入审计，并在回复中告知用户。

**同一轮还发现了两个评测本身的问题**：
- 9 个任务不可解：SOP 要求提供项目名，但模拟用户没有拿到这个信息。已补上，并加测试检查"每个任务都可解""什么都不做必须判失败"。
- 模拟用户越界：没被问到就主动说"帮我建单"。已收紧提示词，并标记越界对话，结果同时报告全量和剔除越界后的两个口径。

**边界**：范围更窄的新申请不会替代范围更宽的旧单（例如先"建单 + 权限"、后"只建单"），这种情况仍可能出现重复工单。

**收获**：单轮评测只看"是否调用了某个工具"，测不出这个问题；按最终状态评分的多轮评测才能暴露它。

## 3. "说做了其实没做"：修复本身也会引入新问题

**发现**：全流程深度评测（110 个业务场景 + 50 个多轮任务）中，同一类问题出现了 4 次：
- 没调用 `create_ticket`，却回复"工单已按你的要求提交"；
- `reset_password` 返回 `success:false`，却回复"待审批请求已生成"；
- 用户说"算了先不申请"，回复"已按你的意思不再推进"，但待审批单仍然挂着。

审批和策略保证了系统**不会做错事**，但没有保证 Agent **不会说错话**。对员工来说，以为已经提交、其实没有，会直接耽误处理。

**定位**：原有守卫只靠一条正则 `已(经)?(为你|帮你)?(提交|创建|生成|发起)…`。中间插一句"按你的要求"、语序换成"请求已生成"、换成撤回类说法，都会漏判。它也不区分是哪一类写操作成功了。

**改动**（`agents/prompting.py::claim_problems`）：按句识别声明，按工单/权限/重置/解锁/锁定分类，再对照本轮**同类**写工具是否成功。写工具失败而回答没提时，要求模型说明原因。纠正一次后仍不一致，就在末尾追加确定性的"【以审批记录为准】"说明。新增 9 个单元测试，全部取自评测中的真实回答。

**修复带来的两个副作用**（重跑时发现，都已修正）：
1. 纠正撤回类声明时，提示断言"已提交的申请仍在待审批"，可当时根本没提交过，模型就编出了一条不存在的申请。现在只有本会话确实建过审批时才核对撤回声明。
2. 对复述过去的句子做纠正，模型把"本轮没提交"说成了"昨天那次也没提交成功"。现在意图识别判定本轮没有要求写操作时，不做核对。

**结果**：针对的缺陷在定向复查里全部通过。多轮模拟 177 轮回复中，纠正触发 26 次，逐条核对都是正确的。总通过数 strata 60→62、hard 43→44、多轮 41→43（每组 1 次，差异只有几个用例，**不能算显著提升**）。能确认的是：这几类虚假声明在之后的三次运行里没有再出现。

**收获**：守卫的纠正提示本身也是一段 prompt，同样会诱导模型编造。所以修复也要用评测去回归，不能只看目标用例过了没有。

## 4. 长对话成本：钱花在了看不见的地方

**发现**：先发现的是评测框架的问题。`evaluation/application.py` 启动时会关掉后台记忆维护（原意是避免短套件混入无关的模型调用），导致第一次长对话运行根本没有触发压缩：早期事实滑出窗口后丢失（2 个回忆探针失败），缓存命中率从 0.7 掉到 0.3。加了 `maintenance` 开关后重新跑。

**定位**（token 审计按组成部分拆开每次调用）：84 轮共 $0.0686，其中后台的画像提炼占 26%。问题集中在用户画像：
- 画像在提示词里从第 4 轮的 1,855 字涨到最长 6,169 字，比知识库预取结果还长，而且每轮都按未命中缓存的价格计费。原因是存储格式被整份 dump 成 JSON，同一事实出现三遍。
- 每次提炼都让模型重写整份画像，平均输出 433 token，输出又按更贵的价格计费。

**改动**（`memory/conversation_memory.py`，schema 4）：画像改成 4 个字段的短文档（背景、工作内容、设备与环境、沟通偏好），每项一句话、限 80 字，每次在旧版本上整份修订。中间版又暴露了两个问题：一是把助手回答也给了提炼模型，结果画像写进了"偏好先给结论"，那其实是系统规则，不是员工的偏好；二是把"反复蓝屏"这种一次性故障写成了长期画像。两处都已修正。

**结果**（同一组 84 轮）：回忆探针 19/19、写操作终态 4/4 不变；画像平均长度 2,654 → 42 字；画像提炼费用 −88%；**总费用 −45%**。

**同一时期还做了一项测量**：开思考在 160 个用例上没有可测量的准确率收益，成本却是 1.5–3.5 倍、首字时延翻倍，所以默认关闭（§10）。技能渐进式披露实测比全量更贵（+12% ~ +17%），因为全量放在 system 里几乎全部命中缓存。

**边界**：4 个脚本化会话，各跑 1 次；画像质量只人工读了 4 份。

## 5. 意图识别"留出集满分"：主动拆掉自己的好看数字

**发现**：README 里写着"留出集 75/75"。回看 CHANGELOG，发现分类 prompt 的类别边界是看过 test 错例之后补上的，补完才从 71–72/75 变成 75/75。也就是说，这个"留出集"参与过调优。

**改动**：新建 83 条盲测集 `intent_v4_blind`，覆盖 12 个维度。编写时不参考 v3 的错例和当前 prompt，标注在第一次运行前定稿并记录哈希，规定"只运行、不据此修改识别逻辑"。

**结果**：
- 宽松口径还是 83/83。说明满分不全是泄漏造成的：22 类意图本身不难，加上"可接受意图"给得宽，宽松口径测不出差别。
- **严格口径 88.0%，比 v3 的 97.4% 低约 10 个点**，这才是泛化差距。主要错误是病毒弹窗、U 盘被禁、打印机、笔记本丢失这类问题被归成 `device_failure`，根因是类别体系缺少安全事件和外设类别。
- 低置信度转 LLM 净多对 3 条（拼音 "mima wangle"，Jev 判成了 greeting），代价是 p95 从 0.59 s 升到 2.07 s。

**边界**：盲测集仍然是作者编写的，排除了调参泄漏，排除不了出题偏差。这些问题都没有依据盲测集去修；修了之后要报分，需要另建一份新的盲测集。

**可能被追问**：为什么不把盲测集上的错误修掉、把分数做到 100%？因为一旦依据它修改，它就和 v3 一样不再是留出集了。

## 6. pass^k：单次成功率掩盖了可靠性问题

**起点**：多轮评测一直只跑 1 次，模拟用户和 Agent 又是同一个模型。被问"你怎么知道改动有效""失败是 Agent 的还是模拟器的"时答不上来。

**改动**：给评测脚本加 `--user-model`，模拟用户分 deepseek-flash 和 deepseek-v4-pro 两组，每组跑 3 遍，按 τ-bench 的无偏估计计算 pass^k。300 个任务约 $0.33。

**先发现的是评分失真**：第一次统计 pass^1 只有 0.73–0.78，最大失败项是"没查资产"。实际上 Agent 查了，只是用了不带参数的"列出本人设备"，这是 HEAD 提交刚加的工具用法，评分脚本没跟上。修正评分规则并补测试后，原始分和重新计分两个口径都保留在报告里。

**结果**：
- 两种模拟用户下 pass^1 都是 0.87，Agent 的表现稳定；但 **pass^3 只有 0.74–0.76**，可靠性比单次成功率低约 11 个点。
- T3（3 个子任务）pass^3 只有 0.50–0.67，是明显的难点。
- 换模型没有减少模拟用户越界，反而从 16 次升到 25 次。所以测量质量的瓶颈在模拟器的约束，而不在用哪个模型。

**找到的真缺陷**：一轮里的多个写操作会被捆成一张审批。用户后来补充信息时，Agent 单独重新提交，旧的捆绑单无法被替代，审批后就多出一张工单。这个边界早就记在文档的"未完成"里，这次第一次量化：最典型的任务在 6 次运行中失败 4 次。

**修复与验证**：只要新申请和旧单有共同的动作，就替代旧单，旧单里没被覆盖的动作另生成一张"余下部分"的申请，沿用原冻结参数和期限，已投的票不带过去（[ADR 0007 修订](adr/0007-supersede-pending-approvals.md)）。用同样的 3 遍 × 2 种模拟用户重跑：重复执行从 7 次降到 0 次，T3 pass^1 从 0.69–0.81 升到 0.81–0.92，pass^3 从 0.50–0.67 升到 0.58–0.75。但 T3 合计 54/72 → 62/72 的 Fisher 检验 p = 0.14，**不能说显著**。

**可能被追问**：
- 为什么不直接把每个写动作拆成单独的审批？那样审批人一轮要处理好几张卡片，"一次请求一张单"的体验和审计粒度都变了。拆分替代只在补充信息时才生效。
- 为什么已投的票不带过去？票是投给旧单哈希的，余下部分是一张新的冻结请求。带过去就等于审批人批准了一个他没看过的组合。
- 重跑还发现了什么？Agent 会自己把被拒的管理员权限改成 developer 写进草稿，用户一句"确认提交"就带着它一起提交了。这和"默认填 reporter"属于同一类问题：影响授权范围的字段由 Agent 自己补了。

## 这几次迭代的共同点

- 每一次都是**评测先发现问题**，而不是先有改动想法、再找数据来证明。
- 有两次问题出在评测本身（不可解的任务、被关掉的记忆维护），一次出在修复本身（纠正提示诱导编造）。所以评测脚本和修复都需要被验证。
- 结论都带着样本量和运行次数。差异只有几个用例时，不说"提升"。
