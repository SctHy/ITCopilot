# 成功率下降排查

1. 先看告警的时间、租户、渠道和样本量。小样本的成功率变化不能直接当作故障。
2. 执行归因脚本。时间必须显式给出时区；两个窗口不重叠：

   ```sh
   IT_COPILOT_DATABASE_URL=... .venv/bin/python scripts/attribute_success_drop.py \
     --baseline 2026-11-01T00:00+08:00/2026-11-08T00:00+08:00 \
     --current 2026-11-08T00:00+08:00/2026-11-09T00:00+08:00 --tenant default
   ```

3. 先看变更时间线：部署、模型路由、策略、技能、知识库、工具、灰度。双比例检验是探索性定位，不证明因果，也未做多重检验校正。
4. 查看 Top 切片。`rate` 是切片本身失败率的变化，`mix` 是流量构成变化。每个维度独立分解；不能把不同维度的贡献相加。新切片无基线，报告将其计入 mix 并标记不可比。
5. 打开失败样本的 `/trace/{request_id}`；过期 trace 用 badcase 快照。对照工具错误类别、轮数、输入 token 和缓存命中率。缓存命中率下降超过 10 个百分点时，优先核对 prompt/tools 指纹。
6. 版本问题走灰度回滚；下游问题看熔断、适配器和返回码；模型服务问题检查路由切换。纯流量变化结合意图组判断产品覆盖，不能仅凭整体成功率宣布版本退化。
7. 将确认的根因回填 badcase 标注，转成可复现回归用例，再验证修复。

报告输出 Markdown 到 stdout，元数据 JSON 存在 `evaluation/reports/attribution_<UTC>.json`。脚本以运营身份只读全局数据；使用 `--tenant` 收窄查询。它不会写业务状态。

缓存命中率下降超过 10 个百分点时，先检查归因报告的 `cache_invalidation`：仅在窗口间 prompt/tools 指纹集合变化时提示优先核查；没有 token 观察时保留空值，指纹变化本身不证明因果。
