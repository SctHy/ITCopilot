**最重要的发现：Agent 的回复与业务状态不一致，同一类问题出现 4 次。**

- 根本没调用工具，就说"已提交建单申请"：`c2-status-ticket`、`c2-grant-status`。
- 工具调用失败（`reset_password` 返回 `success:false`），却说"密码重置待审批请求已生成"：`t2-08`。
- 用户说"算了先不申请"，回复"已按你的意思不再推进"，待审批单却没有撤回：`m-cancel-then-ask`。

现有的审批、策略、职责分离保证了**不会做错事**，但没有保证**不会说错话**。对员工来说，"以为已经提交、其实没有"会直接耽误处理。

### 2.4 真实企业文档检索（GitLab 公开 Handbook）

- 语料：GitLab Handbook 的 corporate IT（服务台、Okta、权限申请、设备）、安全、业务系统三部分，共 540 篇、7,742 个片段，固定在 commit `7a669fd`，许可证 CC BY-SA 4.0。
- 查询：文档里 GitLab 员工自己写的 124 个 FAQ 问题标题，标注是"问题所在的文档"。**出题和标注都不经本项目作者之手。**
- 防泄漏：建索引前删掉所有问题标题行，查询只能靠答案正文召回。

| 模式 | Hit@1 | Hit@5 | MRR | 答案片段 Hit@5 | p50 |
|---|---|---|---|---|---|
| BM25 | 0.56 | 0.81 | 0.66 | 0.44 | 1 ms |
| 向量 | 0.66 | 0.85 | 0.75 | 0.52 | 15 ms |
| 混合（默认） | 0.67 | **0.90** | 0.76 | **0.51** | 14 ms |

按章节（混合检索）：

| 章节 | 查询数 | Hit@1 | Hit@5 | 答案片段 Hit@5 |
|---|---|---|---|---|
| 业务系统指南 | 69 | 0.77 | 0.97 | 0.55 |
| **IT 服务台（eta/corporate-it）** | 41 | **0.44** | **0.78** | **0.41** |

- **IT 服务台明显更难**：Okta、权限申请、Google 账号等主题分散在几十篇相互重叠的文档里，真实企业文档就是这样。自写的 32 篇知识库每个主题只有一篇，测不出这个问题。
- **找到对的文档 ≠ 拿到答案**：文档命中 0.90，但前 5 个片段里真正含答案的只有一半。Agent 读到的是片段，所以这是更接近最终效果的指标。可能的原因是 500 字的切片没有带上小节标题。由于测试时删掉了问题标题，这个指标略偏悲观。
- 有部分"未命中"是标注噪声（例如 "Where do I go if I have any questions?" 可以由多篇文档回答），所以以上都是下限。
- 干扰实验：把 540 篇 GitLab 文档混进 61 篇自写语料后，40 个自写中文查询的混合检索 Hit@5 仍为 1.0，Hit@1 从 0.95 降到 0.925。**这个结论不成立**：干扰文档是英文、查询是中文，跨语言干扰天然很弱，不能据此说系统抗干扰。

## 9. 修复与回归（P0 + 三个 P2）

### 9.1 根因

原有的守卫（`unbacked_write_claim`）只靠一条正则 `已(经)?(为你|帮你)?(提交|创建|生成|发起)…` 识别"已提交"：

| 用例 | 回复原文 | 原守卫的问题 |
|---|---|---|
| c2-status-ticket / c2-grant-status | "已**按你的要求**提交…" | 插入语不在白名单里，漏判 |
| t2-08 | "密码重置待审批请求**已生成**" | 语序颠倒，漏判；也不区分"哪类写操作成功了" |
| m-cancel-then-ask | "已按你的意思**不再推进**" | 撤回类声明不在检查范围内 |
| E14 | "更正：我上一轮没有提交…" | 误判"你已提交的工单"后，纠正提示让模型写出了"更正" |

### 9.2 改动

- `agents/prompting.py::claim_problems`：按句识别声明；否定/计划只看所在分句（"已提交（审批通过后才生效）"仍算声明）；排除主语是用户的句子；按工单/权限/重置/解锁/锁定分类，对照本轮**同类**写工具是否成功；写工具失败而回答没有说明时，把失败原因交给模型；撤回声明只在本会话确实建过审批时才核对（从没提交过时"不再推进"是实话）；意图识别判定本轮没要求写操作时不核对，因为这时多半是在复述过去，强行纠正会制造新的错误（t-past-ticket）。
- 纠正提示写明具体不一致之处，并禁止提"核对/更正"；纠正一次后仍不一致，就在末尾追加"【以审批记录为准】…"。新指标 `it_copilot_agent_claim_checks_total{outcome}`。
- 输出前的确定性处理：去掉模型伪造的 `[本轮工具：…已生成待审批 …]` 执行记录（t2-13 里出现过）；用户本轮贴出的密码/验证码替换为 `******`。
- 纯英文消息在本轮提示里明确要求英文回复。只靠系统提示里的规则不够，第一次重跑 E16 仍然是中文。
- 新增 9 个单元测试，全部来自本次评测的真实回答。

修复过程中重跑发现过两次**修复本身带来的副作用**，都已修正：
1. 撤回纠正断言"已提交的申请仍在待审批"，可当时根本没提交过，模型就编出一条不存在的申请（l-two-requests-one-cancelled）。
2. 对复述过去的句子做纠正，模型把"本轮没提交"说成了"昨天那次也没提交成功"（t-past-ticket）。

|---|---|---|
| strata_v3（64） | 60 | 62 |
| hard_v4（46） | 43 | 44（t-past-ticket 按修正后的 `forbid_text` 重新计分） |
| simulated_v4（50） | 37 原始 / 41 校正评分误判后 | 43 |
| simulated_v4 剔除模拟用户越界 | 37/41 | 41/44 |

- 针对的缺陷在最终代码的定向复查里全部通过：c2-status-ticket、c2-grant-status、s-password-pasted、t-past-ticket、t2-08、t2-13、t3-02，以及 E14、E16。

## 10. 思考档位与 token 优化（2026-11-12）

### 10.1 DeepSeek 的思考参数（官方文档，2026-11 查询）

- `thinking.type`：`enabled` / `disabled`，**默认开启**；`reasoning_effort`：`low` / `high` / `max`，默认 `high`（`minimal`→`low`，`medium`/`xhigh`→`high`）。没有 token 预算参数。
- 思考模式不支持 `temperature`（不报错但无效）；带工具时之前各轮的 `reasoning_content` 要传回（PydanticAI 2.64 会自动处理，实测无 400）；指定函数的 `tool_choice` 会被拒绝，所以意图识别等结构化输出必须保持关闭。
- 实测思考 token 计在 `completion_tokens` 里，按输出价计费。deepseek-flash 非高峰价：缓存命中输入 $0.003、未命中 $0.15、输出 $0.6（每百万 token），高峰时段 ×2。

新增 `IT_COPILOT_AGENT_THINKING`（`disabled`/`low`/`high`/`max`）只作用于 Agent；开启时输出上限放宽到 16000。

### 10.2 Token 审计：钱花在哪

`evaluation/token_audit.py` 在 OpenAI SDK 层拦截每次调用，记录各组成部分的字符数和服务端返回的真实用量；三个业务评测脚本默认开启。基线（旧 prompt、关闭思考）的 Agent 调用：

| 组成 | 平均字符数 | 缓存 |
|---|---|---|
| 工具定义 | 2,730 | 命中（固定前缀） |
| system（规则 + 技能） | 875 | 命中 |
| 本轮消息（预取知识 + 实体 + 背景） | 650–830 | **不命中** |
| 本轮内的工具调用/返回 | 260–590 | 部分命中 |

缓存命中率 81–86%。**成本里输出约占 55–65%，未命中的输入约占 31–42%，命中缓存的输入只占约 4%。**所以缩短固定前缀（system、工具定义、技能）几乎不省钱；该压的是输出和本轮消息。

### 10.3 做了的优化

| 改动 | 依据 |
|---|---|
| 规则加"要调用工具就直接调用，不写过渡语" | 体验测试 26 轮里 8 轮先输出过渡语再调工具，前端清掉但照样按输出计费 |
| 回复长度"每个问题一般不超过 200 字"（原 300） | 回复中位数 351 字，超过原规则；体验评分 E01/E17 被扣"偏长" |
| 预取知识从 JSON 改为紧凑文本（`knowledge_text`），citation 里已有标题，不再单列 | 这一节每轮都不命中缓存；同样内容字符数 −41% |
| 情景记忆加余弦距离门槛 0.6，改为按"相关度 × 重要度"排序 | 原先只按重要度排序、没有门槛，老用户每轮都会带上 3 条无关旧对话（放在不命中缓存的本轮消息里）。门槛来自 9 条查询 × 5 条记忆的小样本校准：同主题 0.19–0.62，不同主题 ≥0.62 |
| 技能支持 `full` / `progressive` / `auto` 三种披露方式，默认 `auto` | 见 10.5 |

评估过但**没做**的：
- 让历史对齐上一轮的真实请求，以提高缓存命中：跨轮时前缀一直命中到上一轮的用户消息，真正不命中的只有最近一对问答；上一轮的回答从未出现在任何请求里，对齐了也命中不了。只能多命中约 40 字，却要把旧的知识检索结果带进上下文。
- 减少写守卫误拦和纠正轮次：50 个多轮任务里分别只有 2–3 次和 14–15 次，占 Agent 调用的约 5%。

### 10.4 结果：4 个思考档位 × 160 个用例（优化后 prompt），外加旧 prompt 基线

三组合计（strata 64 + hard 46 + simulated 50）：

| 档位 | 通过 | strata / hard 每用例成本 | simulated 每任务成本 | simulated 时延 p50 / p95 |
|---|---|---|---|---|
| 基线（旧 prompt，关闭思考） | 148 | $0.000335 / $0.000387 | $0.00104 | 13.4 s / 26.6 s |
| **disabled（优化后）** | **151** | **$0.000334 / $0.000353** | **$0.00096** | **12.4 s / 22.4 s** |
| low | 147 | $0.000487 / $0.000639 | $0.00171 | 19.9 s / 37.4 s |
| high | 147 | $0.000533 / $0.000722 | $0.00217 | 25.7 s / 45.8 s |
| max | 149 | $0.000663 / $0.000971 | $0.00335 | 29.5 s / 111.6 s |

- **开思考没有可测量的准确率收益**：差距只有 2–4 个用例，在单次运行的波动（±2–4）内。逐个用例看，翻转基本是随机的，没有一类问题"开思考就稳定通过"（最接近的是 c-two-docs 和 n-explain-only）。
- 成本 1.5–3.5 倍、时延 1.4–2.4 倍。多出来的不只是思考 token（多轮每任务 low 819、high 1,289、max 3,294）：Agent 调用次数也变多（每任务 5.9 → 7.3 次），回复也更长。
- **优化后 prompt 对比基线（同为关闭思考）**：总输入 token −5% ~ −10%，输出 −10% ~ −13%，时延 p50 −6% ~ −10%，每用例成本 0% ~ −9%，通过率 151 对 148（持平）。成本降得比 token 少，是因为这次运行的缓存命中率低了 0–5 个百分点。DeepSeek 前缀缓存是尽力而为，运行之间的命中率波动比 prompt 压缩的收益还大；所以衡量 prompt 优化看总输入 token，命中率单独看。

用户感知（真实体验 20 组、26 轮）：

| 档位 | 首字 p50 / p90 | 整轮 p50 / p90 | 每轮产品成本 | 每轮输出（含思考） |
|---|---|---|---|---|
| **disabled** | **1.29 s / 2.38 s** | **2.48 s / 3.75 s** | **$0.00035** | 241 |
| low | 2.73 s / 4.61 s | 3.40 s / 6.33 s | $0.00049 | 469（思考 207） |
| high | 3.01 s / 5.74 s | 3.98 s / 7.26 s | $0.00057 | 532（思考 256） |
| max | 3.65 s / 6.88 s | 4.61 s / 8.40 s | $0.00071 | 798（思考 544） |

**选择：`disabled`**。准确率相同的前提下最便宜、最快；开思考后首字时延翻倍，对服务台对话体验影响明显。思考档位适合以后出现"开思考才能稳定解决"的任务类型时，再按意图单独开启。

### 10.5 技能渐进式披露：实测比全量更贵

同一套 strata + hard、关闭思考，`full` 对比 `progressive`：

| 模式 | 通过 | 总输入 / 用例 | 缓存命中率 | 每用例成本 |
|---|---|---|---|---|
| full（全部正文进 system） | 62 + 44 | 4,620 / 5,707 | 81% / 83% | $0.000334 / $0.000353 |
| progressive（system 放目录，相关正文进本轮消息） | 61 + 44 | 4,377 / 5,688 | 75% / 77% | $0.000375 / $0.000413（+12% / +17%） |

技能总共只有 546 字，放在 system 里几乎全部命中缓存；挪进本轮消息后按未命中价计费（单价 50 倍），省下的字数抵不过。粗算的平衡点是：每轮只需要其中 1/50 的技能正文时，渐进式才开始省钱。所以默认 `auto` 在技能总量 ≤ 6000 字时用 `full`，技能多到稀释注意力或放不下时再切换为 `progressive`。

### 10.6 局限

- 每个档位只跑 1 次，单个用例的结果有波动；结论是"没有可测量的收益"，不是"思考没有用"。
- 意图识别走 Jev（TypeSafe），这部分费用不在统计内。
- 记忆门槛校准样本很小；评测里都是新身份，测不到老用户的记忆负载，只有单元测试覆盖。
- 价格按非高峰价计算；高峰时段所有档位同比 ×2，相对结论不变。

## 11. 长对话评测与记忆 token 优化（2026-11-12）

### 11.1 方法

`scripts/evaluate_long_dialogue.py`：4 个脚本化会话，共 84 轮（18–24 轮/会话），产品自带知识库，真实模型，关闭思考。

| 会话 | 内容 | 判分 |
|---|---|---|
| L1 入职第一周（22 轮） | 十几个流程问题 + GitLab、Jira 两次只读申请 | 6 个回忆探针；待审批恰好是这两条 |
| L2 蓝屏长链（20 轮） | 多次补充信息、粘贴事件日志、建单 | 5 个探针（第 1 轮的 stop code、日志里的事件 ID 等）；恰好 1 张工单 |
| L3 钓鱼 + 设备丢失（18 轮） | 两个高风险流程 | 5 个探针；恰好 1 条锁定 DEV-1001 |
| L4 跳跃短问答（24 轮） | 只问不办，第 1–2 轮给出手机、工号、组别 | 第 21–23 轮回忆；不应有任何写操作 |

- 每个会话都跨过工作记忆压缩点（15 条消息），早期事实只能靠会话摘要和用户画像带到后面。
- 每轮结束后等后台记忆维护（压缩、摘要合并、画像提炼）跑完再发下一轮，模拟真人的打字间隔，token 归属也确定。
- Token 审计新增三类调用：`memory_profile`、`memory_summary`、`memory_merge`。

**评测框架问题**：`evaluation/application.py` 启动后会关掉后台记忆维护（为了不让短套件混入无关的模型调用）。第一次运行因此没有压缩，测到的是"压缩失效"的情形。现在加了 `maintenance=True` 开关，长对话套件开启。这次运行保留为 `long_nomaint.json`：

- 第 1–2 轮的事实滑出 20 条窗口后，又没有摘要承接，2 个探针失败（钓鱼链接标题、所在组别）；
- 窗口每轮滑动一条，历史的第一条每轮都变，缓存命中率从 0.7 掉到 0.3。

### 11.2 基线：钱花在哪

开启维护后基线：探针 19/19，写操作终态 4/4，84 轮共 $0.0686（非高峰价）。

| 部分 | 调用 | 费用 | 占比 |
|---|---|---|---|
| Agent | 102 | $0.0394 | 57% |
| **画像提炼（后台）** | 30 | **$0.0182** | **26%** |
| 意图识别 | 37 | $0.0065 | 10% |
| 摘要 + 合并 | 22 | $0.0046 | 7% |

按提示词组成拆开，问题集中在用户画像：

- **`[用户画像]` 随会话无界增长**：第 4 轮 1,855 字，第 22 轮 5,291 字，最长 6,169 字，比知识库预取结果（约 1,300 字）还长。它在本轮消息里，每轮都按未命中价计费。原因是把存储格式整份 dump 成 JSON：同一事实出现三遍（顶层列表、`stable_attributes`、带 `status/updated_at/importance/source` 的 `facts`）。
- **画像提炼每次让模型重写整份画像**：平均每次输出 433 token（按输出价计费）。实际上 `_merge_profile` 本来就会合并新旧画像，模型只需要给出增量。

### 11.3 改动

**画像改为一份短文档，像 AGENTS.md 一样整份修订**（`memory/conversation_memory.py`，schema 4）：

- 只有四个字段：背景（部门/团队、岗位、资历）、工作内容（项目、常用系统及用途）、设备与环境、沟通偏好。每个字段一句话，写入时限 80 字。进提示词时每个字段一行（`profile_text`）。
- 每次提炼时，模型拿到旧版本和员工最近说的话，返回修订后的完整画像：仍然成立的照抄，冲突的以员工最新说法为准，过时的删掉。合并逐字段替换；修订版漏写的字段沿用旧值。原来的事实列表、`stable_attributes`、`FACT` 状态机（active/superseded）都已删除。
- 提炼输入**只给员工自己说的话**。中间版把助手回答也给了模型，4 个会话里有 3 个画像写了"偏好先给结论再列步骤"，但那是系统规则要求助手采用的写法，不是员工的偏好。
- 明确不写故障、报错、工单、审批（这些由会话摘要和情景记忆负责）。中间版把"反复蓝屏""Wi-Fi 慢""VPN 曾报 691"都写成了长期画像。也不写"未知/未提及"之类的占位。
- 旧的 schema 3 画像读取时就地转换（部门 → 背景，系统 → 工作内容，设备 → 设备与环境，偏好 → 沟通偏好），下次提炼时再由模型修订。

另外两处：

- 会话摘要的提示词要求错误码、事件 ID、设备号、工单号原样保留。中间版有一次把日志里的事件 ID 153 摘丢了，探针失败。
- `history_turns`：超过 20 条时按 10 条一块截断，不再逐轮滑动。只在压缩被推迟（摘要失败或超时）时生效，让失败情况下的历史前缀仍能缓存 5 轮。

| L3 | 背景：工号 1001。／设备与环境：公司配发的笔记本电脑。 |
| L4 | 背景：platform 组成员，工号 1001。／设备与环境：使用 iPhone 和 Mac。／沟通偏好：英文不好，希望用中文回答。 |

这些改动只影响有后台维护、超过 15 条消息的长会话：短套件不开后台维护，没有画像；按块截断也要超过 20 条才触发。所以 §9–10 的结论不受影响，没有重跑。

### 11.5 评估后没做

- **摘要与合并并成一次调用**：每次压缩省一次调用，但整体只占 2–3%。而且分段摘要还要单独写入情景记忆供跨会话检索，合并后语义会变。
- **把摘要和画像移到历史之前以命中缓存**：画像每 3 轮更新一次，摘要每 5 轮更新一次，挪到前面后每次更新都会打断整段历史的缓存。画像只剩几十字，收益已经很小。
- **降低画像提炼频率**（现在每 6 条消息一次）：提炼费用已经降了 88%，每次只占几十个输出 token；频率再降，跨会话记忆就会更新得更慢。

### 11.6 局限

- 用户消息是脚本化的，只有一个人写的 4 个会话，各跑 1 次。
- 探针按关键词判分，只能说明事实被带到了后面，不代表回答质量。
- 后台维护在两轮之间跑完；真实用户回复很快时，维护可能还没完成，下一轮会用到旧的画像。
- 画像质量只看了 4 份，是人工读的；L2 画像为空，偏保守（员工说过"Windows 电脑"，这条本可以写）。跨会话的修订（换部门、换设备）只有单元测试覆盖。

## 12. 意图识别盲测（`intent_v4_blind`，2026-11-12）

### 12.1 为什么要重做

`intent_v3` 的 test 划分不是干净的留出集。CHANGELOG 里有记录：分类 prompt 的类别边界是在看过 test 错例之后补上的，补完 DeepSeek 在 test 上从 71–72/75 变成 75/75。之后 Jev 的阈值、规则表也都在这同一份数据上迭代过。所以 "test 75/75" 衡量的是"调完之后在调参数据上的表现"，不是泛化。

### 12.2 方法

- 新建 83 条用例，覆盖 12 个维度：真实口吻的长叙述、错别字/拼音、体系缺口、易混、否定、一句多诉求、伪装成 IT 的范围外请求、注入、英文、信息不足、长历史多轮、紧急度。标注沿用 v3 的 12 条规则。
- 编写时没有参考 v3 的错例和当前的分类 prompt；标注在第一次运行前定稿，文件 sha256 为 `9c00e6c7…77db11`。
- **使用约束**（写在数据集的 `provenance` 字段里）：只允许运行，不允许依据它修改识别逻辑后再报分。发现标注错误时只能改标注，并记入 `errata`。
- 仍然是作者编写的，不是外部数据。它能排除"调参泄漏"，但排除不了"出题人和系统作者是同一个人"带来的偏差。

### 12.3 结果（各 1 次）

| 路径 | 宽松（含可接受意图） | **严格（只认首选标注）** | 紧急度 | p50 / p95 |
|---|---|---|---|---|
| 生产默认（Jev，置信度 < 0.7 转 LLM；83 条里转了 10 条） | 83/83 | **73/83（88.0%）** | 4/5 | 0.28 s / 2.07 s |
| 只用 Jev（阈值 0） | 82/83 | **70/83（84.3%）** | 4/5 | 0.28 s / 0.59 s |
| 参照：同一生产路径在 v3 上 | 155/156 | 97.4% | | |

报告：`evaluation/reports/intent_v4_blind/{auto,jev_only}.json`（不入库）。

### 12.4 结论

1. **宽松准确率在新数据上也饱和了**。所以之前的满分不全是泄漏造成的：22 类意图对当前模型本来就不难，加上"可接受意图"给得宽，宽松口径基本测不出差别。**以后报意图准确率，以严格口径为主。**
2. **严格口径从 97.4% 降到 88.0%，这约 10 个点才是泛化差距**，主要来自三类：
   - **安全/外设类被归成 `device_failure`**（5 条）：病毒弹窗、U 盘被安全策略禁止、打印机乱码、注入用例里的打印机卡纸，以及笔记本丢失（这一条只在生产路径上错了：Jev 原本判的是 other，转给 LLM 后反而改成了 device_failure）。和 §2.3 真实体验测试的发现一致，问题出在类别体系缺了这几类，不是分类器能力不够（P3：增加 `security_incident`、`device_lost`，打印机等外设另立类别）。
   - **"怎么做"和"出故障"的边界**：例如"别建单，我就想知道 MFA 怎么重新绑定"，按 R4 应标 howto，模型给的是 mfa_issue。
   - **短追问的语义**："算了不弄了"被识别成 ticket_cancel；"这种情况你们能直接帮我弄吗"被识别成 human_handoff。这几条本身也有歧义，算标注口径问题。
3. **低置信度转 LLM 有实际收益**：纯拼音的 "mima wangle"，Jev 判成 greeting，生产路径转给 LLM 后识别正确。严格口径上，转发让 4 条由错变对（mima wangle、"网"、打卡机、财务部报销系统），1 条由对变错（笔记本丢失），净多对 3 条；代价是 p95 从 0.59 s 升到 2.07 s。
4. 笔记本丢失（客户资料外泄风险）的紧急度给的是 high，标注是 critical，两条路径都没给对。

这些问题都**没有**依据本数据集去修。修了之后要再报分，需要另建一份新的盲测集。

复现：`python scripts/evaluate_intents.py --dataset evaluation/datasets/intent_v4_blind.json`（生产路径；有 `TYPESAFE_API_KEY` 时走 Jev 优先）；`python scripts/evaluate_intent_jev.py --dataset evaluation/datasets/intent_v4_blind.json --runs 1`（只用 Jev）。

## 13. 多轮评测的 pass^k 与换模型模拟用户（2026-11-12）

### 13.1 为什么做

§2.2 和 §9 的多轮结果每组只跑了 1 次，而单次运行的波动（±2–4 个用例）和多数改动的效果一样大。另外，模拟用户和被测 Agent 都是 deepseek-flash，"模拟用户越界"和"Agent 出错"很难分开。

### 13.2 方法

- 被测 Agent 固定用 deepseek-flash（关闭思考），数据集 `simulated_v4`（50 个任务），代码为当前工作区。
- 模拟用户分两组：deepseek-flash（与 Agent 相同）和 deepseek-v4-pro（新增参数 `scripts/evaluate_simulated.py --user-model`）。两者是同一家厂商的不同模型，**没有做到跨厂商**。
- 每组独立跑 3 遍，共 300 个任务，3 个进程并行，没有出现 429/402。
- pass^k 用 τ-bench 的无偏估计：对每个任务计算 C(成功次数, k) / C(3, k)，再取平均。
- 报告：`evaluation/reports/passk_20261112/{deepseek-flash,deepseek-v4-pro}_r{1,2,3}.json`（不入库）。300 个任务的审计费用约 $0.33（非高峰价），任务时延 p50 14 s。

### 13.3 先发现的是评分脚本的问题

第一次统计时 pass^1 只有 0.73–0.78，最大的失败项是 `tool_lookup_asset`（40 次）。逐条看下来，39 次都是 Agent 调用了 `lookup_asset` 但**没带 `asset_id`**。HEAD 提交（9c88a20）把这个参数改成了可选，不传时按登录身份列出本人名下的设备，返回里正好有目标设备，后续回答也是对的。可评分脚本仍要求参数精确等于 `DEV-xxxx`。

工具契约改了，评分规则没跟着改。修正方式（`evaluation/simulated.py::_OWN_LISTING`）：不带参数的本人设备列表，只有在目标设备属于员工本人时才算命中，并新增测试 `test_listing_own_assets_counts_as_looking_up_the_target_asset`（包括"别人的设备不算"）。报告保留了 `raw_passed` / `raw_checks`，原始分和重新计分两个口径都能核对。

这是第二次因为产品改动导致评分失真（第一次是 Jev 预取后不再调用检索工具，见 §6）。以后改工具契约，要同时检查评分规则。

### 13.5 39 个失败逐条归类

| 原因 | flash 模拟 | pro 模拟 | 归属 |
|---|---|---|---|
| 模拟用户越界（没被要求就让建单/申请） | 6 | 14 | 模拟器 |
| **同一轮的多个写操作捆成一张审批，后续补充信息时无法被替代**，审批后出现重复工单或重复重置 | 4 | 3 | **Agent/审批层真缺陷** |
| Agent 主动提出"需要我建单吗"，用户顺势同意（越界规则没标出） | 4 | 1 | 有歧义：任务不要求建单 |
| 用户要只读，Agent 按 SOP 默认填 reporter | 2 | 0 | Agent（§5 P2，已知） |
| 一轮回答多个问题时漏了打印机那条的引用 | 2 | 0 | Agent |
| 其他：模型请求超时 1；没调用资产查询 1；模拟用户说"之后再申请"而没推进 1 | 1 | 2 | 基础设施 / Agent / 模拟器 |

**最主要的真缺陷**集中在 T3。`api/routes/chat.py` 把一轮里所有写工具调用合成一张审批。用户第一句话同时提了"开 GitLab 权限 + 蓝屏建单"，生成的就是 {权限, 工单} 一张单。之后用户补充项目名、资产号，Agent 又分别单独提交了权限和工单。`workflow/store.py::_supersede` 只替代"动作集合完全被新单覆盖"的旧单，单独的工单覆盖不了 {权限, 工单}，于是旧单留着，审批人全批之后就多出一张工单。§6 的"未完成"里记过这个边界，这次是第一次量化它的影响：T3 的 t3-10 在 6 次运行中失败 4 次。更糟的是，Agent 在回复里说"更早的申请都已被新申请替代，但仍处于待审批状态"，自相矛盾。

### 13.6 结论

1. **Agent 本身的表现在两种模拟用户下一致**：pass^1 都是 0.87，pass^3 是 0.74–0.76。之前单次跑出的 43/50（0.86）在这个范围内，但**可靠性（pass^3）比单次成功率低约 11 个点**，50 个任务里大约 12 个任务做不到 3 次全对。
2. **换模型模拟用户并没有减少越界，反而更多**（25 对 16），pro 组 T3 的下滑主要是这个原因。剔除越界后 pro 组反而更高（0.95 对 0.90）。所以要提高测量质量，与其换模型，不如加强模拟器的约束，例如对"建单/申请"类请求做确定性的过滤，只在任务目标包含时才允许说出口。
3. **复杂度确实是难点**：T3 的 pass^3 只有 0.50–0.67，而 T1/T2 是 0.71–0.86。T3 的真缺陷基本都来自上面的审批捆绑问题，属于审批层，不在模型。
4. 修复见 §13.7。最初提出的方案是：替代规则改为按动作逐个处理，新单覆盖旧单中的某个动作时，只取消旧单里的那个动作；或者每个写动作单独成一张审批。修完需要用同样的 3×2 设置重跑，比较 T3 的 pass^3。

复现：`python scripts/evaluate_simulated.py --redis-url "" --user-model <模型> --output passk_20261112/<模型>_r<N>.json`，每组跑 3 遍。

### 13.7 修复审批捆绑后重跑（同样 2 种模拟用户 × 3 遍）

**改动**（[ADR 0007 修订](adr/0007-supersede-pending-approvals.md)）：新申请只要和旧单有共同的动作就替代旧单，旧单里没被覆盖的动作另生成一张"余下部分"的申请（`WorkflowStore._carry_over`）。余下部分沿用原冻结参数、状态和期限，审批人数重新计算，已投的票不带过去。新增测试 `test_carried_over_part_keeps_its_own_approval_rule_and_votes_start_over`；原来断言"窄申请不替代宽申请"的测试已按新语义改写。

报告：`evaluation/reports/passk_20261112_fix/`。修复前的数字都按 §13.3 修正后的评分计算。

| | flash 模拟：修复前 → 后 | pro 模拟：修复前 → 后 |
|---|---|---|
| 每遍通过 | 44/41/46 → 45/47/39 | 45/41/44 → 41/43/45 |
| pass^1 / pass^3 | 0.87 / 0.76 → 0.87 / 0.72 | 0.87 / 0.74 → 0.86 / 0.76 |
| **T3 pass^1 / pass^3** | **0.81 / 0.67 → 0.92 / 0.75** | **0.69 / 0.50 → 0.81 / 0.58** |

- **目标缺陷消失**：审批后出现的重复执行（多一张工单或多重置一次密码），300 个试次里从 7 次降到 0 次。
- T3 合计 54/72 → 62/72。Fisher 精确检验 p = 0.14，**不显著**；能确定的只是重复执行这一类失败没有再出现。
- 总体 pass^1 不变，pass^3 一升一降，都在 3 遍运行的波动范围内。T1 的下降来自 t1-00：Agent 先问"需要我建单吗"，模拟用户顺势同意（3 次里有 2 次被标为越界），和本次修复无关。
- 没被标越界的失败里，没有一个和替代/拆分有关。剩下的是：
  - Jira 要只读却按 SOP 填了 reporter，4 次（§5 P2，仍未修）；
  - **新发现**：用户在 P 层任务里说"管理员开不了就算了"，Agent 却自己改成 developer 写进草稿，用户随后的"确认提交"把它一起提交了（p-04，1 次）。Agent 前一轮刚说过"不会把它换成其他角色"。这和 E15、t2-12 是同一类问题：影响授权范围的字段由 Agent 自己补，应该在 §5 P2 里一起修；
  - 用户把解锁推迟到以后，1 次；模型超时，2 次。

**评测上的启示**：这次修复针对的缺陷在 T3 里只占 7/300 个试次，3 遍 × 2 种模拟用户的样本量刚好够看到它消失，但不够证明总体有显著提升。要证明后者，需要专门针对这类场景的任务（例如每个任务都在第一轮捆绑多个写操作，之后再补充其中一个），或者更多遍运行。
