# 0025 多租户：只能收紧的租户策略、租户自己的目标系统、平台管理员

日期：2026-11-12 · 状态：已采纳（补充 0008、0021、0022–0024）

## 背景

阶段 0–2 隔离了数据，但所有租户仍然共用三样东西：

- **一份访问策略**：不能按租户设置审批人数和最长时长；改一次策略，所有租户的在途工作都要被复核。
- **一套执行凭据**：部署的 Gitea 账号替所有租户授权，凭据泄漏的影响范围是全部租户。
- **部署级操作的权限**：技能重载、数据清理、全量策略复核作用于整个部署，但任何一个租户的 IT 管理员都能触发。

## 决定

**租户策略覆盖**（`workflow/policy.py::tighten`）：

- 平台基线仍是 `config/access_policy.yaml`。租户可以有覆盖文件 `config/policies/<tenant>.yaml`，文件名就是租户 id；只有格式合法的 id 才会被当作文件名，`../x` 这类 claim 用的是基线。
- 覆盖只能收紧：
  - 审批人数只能增加；
  - 最长时长、默认时长和各项 TTL 只能缩短；
  - 系统和角色只能删减（设为 `null`）；
  - `approver_roles`、`on_behalf_roles` 只能取基线的子集；
  - `requester_confirmation` 只能在基线上追加。
- 以下情况在加载时拒绝，不会被忽略：基线没有的系统、角色或操作，未知字段，`role_aliases`，没有声明 `version`。
- 编辑出错或放宽时，沿用上一次加载成功的版本；第一次加载就失败时直接报错（fail closed），不会退回基线。
- 没有覆盖的租户就是基线本身，版本号与之前完全相同，升级后不会触发全量复核。有覆盖的租户版本号为 `<基线版本>/<tenant>:<覆盖版本>+<指纹>`。

**每个决定都用所属租户的策略**：

- 冻结、投票、确认、复核、执行前检查、授权到期检查，都按审批单或授权所属的租户取策略（`WorkflowStore.policy_for`）；智能体工具的预检、事项回合、目标核验同理。
- `revalidate(tenant)` 按租户逐个复核：每个租户的在途工作只与本租户的当前版本比较。
- worker 用"基线加所有覆盖"的签名判断策略是否变化，变化后复核全部租户；每个覆盖的生效版本在该租户名下写一条 `policy_loaded` 审计，该租户的管理员能看到。

**租户自己的目标系统**（`config/tenant_adapters.yaml`）：

- 每个租户可以配置自己的 Gitea：地址、仓库，以及存放凭据的**环境变量名**。文件里写明文凭据、或者环境变量没有设置时，拒绝启动。
- 有自己配置的租户，只使用自己的系统。
- 部署通过环境变量配置的 Gitea：单租户模式下为所有人执行，和之前一样；多租户模式下只为运营方租户（`IT_COPILOT_PLATFORM_TENANT`，默认 `default`）执行，其余租户只有本地沙箱。
- 动作入队时按审批单所属的租户选择适配器，与由谁做出决定无关；worker 在动作所属的租户作用域里执行。

**平台管理员**：

- 新增角色 `platform_admin`。多租户模式下，它只在运营方租户内有效：租户自己的 IdP 可以给自己签发任何角色，但签不出这项权限。单租户模式下，IT 管理员就是平台管理员，和之前一样。
- `/skills/reload`、`/ops/retention/run` 需要平台管理员。
- `/policy/revalidate`：租户的 IT 管理员复核本租户；平台管理员复核所有租户。审计记录本次复核的范围。

## 不做的事与原因

- **熔断不按租户拆分**：智能体工具都调用共享的下游，按工具熔断是对的；按租户拆开反而会减弱对共享服务的保护。参数错误（`ValueError`）本来就不计入熔断失败次数。真正按租户区分的下游是执行适配器，它们按动作区分可重试、结果未知和永久失败三种情况，不共用熔断状态。
- **模型看不到哪些系统可申请**：工具 schema 里不列出系统，被租户关闭的系统由工具预检和冻结两次拒绝，所以不需要再对模型隐藏。
- **外部 MCP 服务仍是全局的**（`config/mcp_servers.json`）：所有租户的智能体看到同一组外部只读工具。按租户设置白名单还没有实现。

## 后果

- 有覆盖的租户比基线严格，从不更宽松。一个租户的覆盖编辑只会让该租户的在途工作失效或提高审批人数。
- 迁移 `0004` 之后才有每个租户自己的目录；租户的外部系统同样要求每个动作在正确的租户作用域里执行，否则 `username_of` 报错，不会用别的租户的身份。
- 平台管理员也需要 `it_admin` 角色才能调用 `/policy/revalidate`，因为该接口的入口仍是 IT 管理员。
