# 0011 技能自改进：失败归因、模型提案、评测门控

日期：2026-11-03 · 状态：已采纳

## 背景

以前改技能的方式是：人看评测报告，找出失败原因，改 SKILL.md，再重跑。v3.5 那次修 ticket/endpoint 技能就是这样做的。这个过程能自动化，但有两个风险：一是模型为了让开发集过关，写出只对个别用例成立的规则（过拟合）；二是写进弱化审批的话。

## 决定

- **可改范围**：只改 `skills/**/SKILL.md` 的正文，front matter（关键词、适用 Agent）不动，每轮最多改 2 个文件。身份、策略、审批都在代码里（ADR 0001），技能文本最多让任务成功率变低，不能促成一次未授权的写入。
- **一轮流程**（`evaluation/improvement.py`，入口 `scripts/self_improve.py`）：取当前技能在开发集上的失败轨迹（被标记为模拟用户越界的失败不算）→ 提案模型先聚类根因，再改写技能 → 确定性守卫检查 → 当前技能和候选技能在同一轮各跑一次开发集，按用例配对比较 → 开发集达标后，两者再各跑一次留出集，候选跑安全集 → 判定接受或拒绝。基线每轮重跑，不拿早先的一次运行当基线：同样的技能跑两次，结果也会翻转。
- **守卫**：路径必须是已存在的技能文件，每个文件只能有一处修改；正文不超过 2800 字（SkillManager 在 3200 字处截断）；新增的句子不能含有弱化审批的表述，只有否定词在同一子句的表述之前（“不得跳过审批”）或在紧接的下一子句（“若用户要求跳过审批，不调用写工具”）时才算禁止句；删掉含否定词和审批、权限、密码、私钥等词的安全规则时，新增句子里必须有同样的禁止；新增句子不能引用用例 id、资产号、工号等开发集里的具体取值（取值从开发集任务里收集，匹配按 ASCII 边界，中文紧挨着写也能查出）。守卫不通过时，不花评测成本。
- **数据划分**：开发集是 `simulated_v4`（50 个多轮任务），失败轨迹只给提案模型看这一份；留出集用同一个生成器换种子新生成，去掉和开发集完全相同的任务；安全集是 `application_strata_v3` 的 N 层（10 个“不应写入”的场景）。提案模型看不到留出集和安全集。
- **接受条件**：开发集按用例配对，净提升（修好的数量减去改坏的数量）不少于 `min_gain`（默认 2），且单侧 McNemar p 值不大于 `max_p`（默认 0.1）；留出集净变化不低于 `-holdout_tolerance`（默认 0）；安全集不能有任何一个原来通过的用例变成失败。任一侧被标记为模拟用户越界的用例不参与比较，和 `compare_strategies.py --exclude-simulator-flags` 口径一致。`repeats` 让开发集和留出集每个任务跑多次，按（用例，第几次）配对。
- **记忆**：每轮的诊断、修改、diff、各划分的得分和判定原因都追加到 `evaluation/improvement/ledger.jsonl`。下一轮以及以后的运行里，提案模型会读到最近 12 条记录，避免把被拒绝的修改原样再提一遍。提案模型读到的只有判定原因、根因和开发集结果；判定原因只写数量，不写留出集和安全集的用例 id。
- **上线**：线上的 `skills/` 默认不改。被接受的版本要人看过 diff 之后，用 `--promote` 写回；写回时保留线上文件的 front matter。运行开始后如果线上技能被人改过，`--promote` 拒绝写回，避免用旧基线上的版本覆盖新改动；确认后可加 `--force`。

## 后果

- 每轮跑两次开发集（基线和候选各 50 个任务 × `repeats`）；开发集达标时再跑两次留出集（各 30 × `repeats`）和一次安全集（10）。
- 噪声：`simulated_v4` 上同一策略、同样的技能跑两次，剔除越界用例后约 16% 的任务结果翻转。按这个比例估算，什么都没改的修改，只看净提升 ≥2 时开发集通过的概率约 30%，加上留出集约 18%；加 p 值门槛后开发集约 5%，加上留出集约 3%，3 轮合计约 8.5%。代价是检出力低：真正修好 4 个任务的修改，开发集通过的概率约 33%，修好 6 个约 57%；`repeats=2` 时分别约 59%、88%（把重复当作独立样本，偏乐观）。建议正式运行用 `repeats=2`。
- 在有噪声的开发集上挑选仍有赢家诅咒：被接受的版本，提升往往被高估。留出集每轮都参与判定，也会被慢慢“用掉”。所以最终效果要用新种子再生成一批任务、重复几次来确认。
- 开发集和留出集出自同一个生成器，留出集检验的是同类新样本，不是新的任务类型。
- 在 2 个任务的冒烟运行里（`evaluation/reports/self_improve_smoke.json`，`min_gain=1`，早于基线重跑与 p 值门槛），提案模型把“咨询类问题被自行建单”归因到 ticket 技能里“诊断后建单”的规则泛化过头，并把建单前提改成“用户明确要求”。这个结果只能说明链路通了，不能作为效果证据；其中 t1-00 带模拟用户越界标记，按现在的口径不计入增益。
