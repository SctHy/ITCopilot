# 0007 同一会话的新申请替代仍待审批的旧申请

日期：2026-10-29 · 状态：已采纳

## 背景

多轮状态评测（docs/evaluation.md 第 6 节）中，用户补充信息、再次说“确认提交”，或要求“补充进工单”时，agent 会重新调用 `create_ticket`。每次调用都会生成一张新的待审批单，审批人逐张批准后就出现重复工单。修复前有 247 段对话，其中 73 段因此失败，占全部 101 个失败的 72%，四种策略都有。

## 决定

- `WorkflowStore.create` 在写入新审批的同一事务里，查找同一会话、同一申请人、仍为 `pending` 的旧审批。如果旧审批的全部动作都被新审批覆盖，就把旧审批标记为 `superseded`。
- “覆盖”按动作键判断：工具 + 目标员工；`request_access` 再加系统。
- 更新带版本号条件：审批人同时决定旧单时，以审批人的决定为准。
- 被替代的审批不能再被批准。双方都记审计（`superseded` / `supersedes`），回复中告知用户。

## 后果

- 修复后的多轮评测中不再出现这类重复工单；用户在同一会话里确实要办的不同事情（例如不同系统的权限）不受影响。
- ~~新申请范围更窄时不会替代范围更宽的旧单~~：已由下面的“2026-11-12 修订”解决。
- 跨会话的重复申请不在范围内。

## 2026-11-12 修订：部分覆盖时拆分

**问题**：一轮里的多个写操作会合成一张审批（`api/routes/chat.py`）。用户第一句话同时说"开 GitLab 权限 + 蓝屏建单"，生成的就是 {权限, 工单} 一张单；之后补充信息时 Agent 分别单独重新提交，单独的工单覆盖不了这张捆绑单，审批人全部批准后就多出一张工单（或多重置一次密码）。多轮评测 2 种模拟用户 × 3 遍里，这是最主要的 Agent 侧真缺陷（docs/evaluation-deep.md §13）。

**决定**：只要新申请和旧单有共同的动作键，就替代旧单；旧单里没有被覆盖的动作另生成一张"余下部分"的申请（`WorkflowStore._carry_over`）：

- 动作沿用旧单冻结的原参数，申请人、会话、策略版本、状态（草稿仍是草稿）、过期时间都与旧单相同。申请人没有新内容需要确认，期限也不会因此延长。
- 审批人数按余下的动作重新计算；旧单上已投的票不带过去，因为票是投给旧哈希的。
- 审计：旧单的 `superseded` 记录 `remainder`，新生成的那张 `created` 记录 `carried_from`。回复中告诉用户哪些事项被保留了。

**后果**：
- 同一件事不会再因为捆绑而重复；用户还想办的其他事项不会被丢掉。
- 已经投过票的审批人需要对余下部分重新投票。
- 余下部分不会出现在共享事项的讨论卡片里（共享事项只接收原审批的事件），仍然可以在审批页看到并处理。
