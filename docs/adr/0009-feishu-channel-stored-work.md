# 0009 飞书入口：先落库再处理，只在被叫到时说话

日期：2026-11-03 · 状态：已采纳

## 背景

员工报障大多发生在 IM 群里，而不是专门的网页上。接入飞书机器人要解决几个问题：飞书要求 3 秒内响应回调，超时会重推，但一轮对话要 6 秒左右；进程崩溃不能丢消息，也不能重复回复；发送者身份必须可信；群里的闲聊既不能触发 Agent，也不应该被存下来。

这里参考了 DeepSeek dsh-superagent 的 Source / Thread / Channel 抽象，以及它的两条原则：所有对外动作先存储再执行；尽量少占用人的注意力。

## 决定

- **入站**：`POST /channels/feishu/events` 收到事件后，先校验 verification token，配置了 Encrypt Key 时再校验签名并解密，然后过一道准入门，通过的消息写入 `channel_inbox` 后立即返回。主键是消息 ID，所以飞书重推的同一条消息只会落库一次。后台按租约领取消息，再走和 `/chat` 完全相同的对话路径。`client_request_id` 取消息 ID，崩溃后重跑会直接返回已存的回执。
- **准入门**：只有以下三种消息会被受理：私聊；群里 @ 机器人；同一个人在自己发起的话题里继续回复（追问不需要再 @）。机器人发的消息，包括它自己的，一律丢弃。群里没有叫到机器人的消息不落库。可以用 `FEISHU_ALLOWED_CHATS` 限定监听哪些群。
- **身份**：发送者身份只取自飞书事件头里的 `user_id` / `open_id`，按 `config/feishu_users.yaml` 映射为 Principal。消息正文不参与身份判断。没有映射的人只会收到一句“未绑定”的回复。映射里的 `subject` 与网页登录一致，所以网页和飞书看到的是同一份审批和记忆。
- **会话**：私聊是一个持续的会话。群里每次 @ 开一个话题，机器人在话题里回复，话题内的回复延续同一个会话。同一会话的消息按顺序逐条处理。
- **出站**：回复和审批结果通知都写入 `channel_outbox`，由渠道服务发送。同一会话内按序号依次发出；前一条连续失败 3 次后，不再阻塞后面的消息。临时失败从 5 秒开始退避，最长 300 秒；永久失败（消息被撤回、机器人被移出群）直接丢弃，但保留记录。飞书的 `uuid` 字段用于去重，重发不会出现两条。
- **审批通知**：`WorkflowStore.notify` 钩子在审批状态变化的同一个事务里写入通知，覆盖拒绝、过期、策略失效、执行成功、执行失败、待人工核对。独立 worker 进程也会挂上这个钩子，所以它执行完的审批同样会通知到飞书。
- **注意力预算**：一次请求最多打扰员工三次：收到时加一个表情回应（不产生通知），给出一条答复，审批有结果时再发一条通知。`/monitor` 的 `channels` 字段只列出需要人处理的问题：处理失败的消息、持续发不出去的消息。

## 后果

- 回调路径只做校验和写库，不调用模型，能稳定在飞书的 3 秒时限内返回。
- 平台重推、进程崩溃、发送超时都不会导致重复回复。测试见 `tests/test_feishu_channel.py`。
- 身份映射需要手工维护。生产环境应改为通过飞书通讯录（邮箱或工号）对接企业目录。
- 回调地址需要公网可达（本地开发可以用内网穿透）。飞书的长连接模式（WebSocket）不需要公网地址，目前没有实现。
- 只处理文字和富文本中的文字，图片暂不识别。
