# 0024 多租户：每个租户一个知识库

日期：2026-11-12 · 状态：已采纳（补充 0022、0023）

## 背景

知识库全局只有一份，只按部门过滤，`department="*"` 对所有人可见。跨租户巡检（ADR 0022）确认，另一个租户的管理员能列出、检索、删除本租户的文档；反过来，他上传的文档也会出现在本租户的检索结果里。另外，`knowledge_search` 的结果缓存按参数和上下文生成 key：两个租户发出相同的查询，会命中同一条缓存。

## 决定

- **每个租户一个库**：`KnowledgeLibrary` 是一个租户的文档，对应自己的向量 collection 和自己的 BM25 索引；`KnowledgeBase` 按租户把调用转给对应的库。
  - `default` 继续使用原来的 collection `knowledge_base`，不用迁移数据；其他租户使用 `knowledge_base:<tenant>`。
  - 演示文档只导入 `default`。
  - 部门过滤只在一个租户的库内生效，`*` 的含义变为"本租户全员可见"。
- **选库方式是命名空间，不是 tenant 列**：各租户的检索互不共享候选集，BM25 的 n、avgdl、df 也只在本租户的文档里计算，一个租户的文档不会影响另一个租户的排序。代价是 `vector_documents` 没有 RLS（ADR 0023），只靠 collection 名隔离。
- **租户从哪里来**：
  - 调用方显式传入；
  - 否则取当前的租户作用域，也就是请求的调用者；
  - 两者都没有时，单租户模式用 `default`，多租户模式报错。
  - `knowledge_search` 的参数里没有 tenant 字段，模型和被注入的文档都无法指定租户。
- **管理接口**：`/knowledge/add`、`/knowledge/upload`、`/knowledge/documents`、删除文档都只作用于管理员所在的租户。`/knowledge/stats` 改为需要登录，因为片段数按租户统计，匿名请求没有租户。
- **工具结果缓存**：缓存 key 里加入当前租户作用域。

## 后果

- 巡检已知缺口全部关闭：知识库的列出、检索、删除已经移到探测清单；只作用于本租户的测试还验证了反方向，另一个租户上传的文档在本租户既检索不到、也不计入片段数。变异测试：去掉缓存 key 里的租户后，巡检立即发现另一个租户命中了本租户的缓存结果。
- **行为变化**：匿名调用 `/knowledge/stats` 现在返回 401，前端本来就会带令牌。
- `/mcp`（只读的 MCP 服务端）没有鉴权、也不知道调用者的租户：单租户部署检索 `default` 的公共文档，和之前一样；多租户模式下检索直接报错，不会去查任何一个租户的库。MCP 要支持多租户，需要先给它加上身份认证。
- **未实现**：平台公共知识库（`_platform` 租户 + 租户显式订阅）。目前租户之间不共享任何文档，需要通用 SOP 的租户各自导入。
- 情景记忆和用户画像在同一张向量表的其他 collection 里，按 `scope_key`（租户 + subject 的哈希）隔离，这次没有改动。
