# 0008 策略变更后复核在途审批与授权

日期：2026-11-03 · 状态：已采纳

## 背景

审批创建时冻结了当时的策略版本（ADR 0001），但冻结之后发生的事以前没人管：策略收紧（例如撤掉某个角色、把最长有效期从 168 小时改成 24 小时）后，按旧规则提交、还在待审批的单照样能被批准；已批准、还没执行的动作照样会执行；已经生效的限时授权也照旧有效到原定时间。另外，策略只在进程启动时读一次，改文件后要重启才生效。

这个做法参考了 DeepSeek dsh-superagent 的 Mandate：授权凭证本身不可变，策略变化时通知受影响的在途工作，恢复执行前按当前策略重新校验。

## 决定

- `load_policy()` 按文件修改时间缓存，改 `config/access_policy.yaml` 后下一次调用就能读到新版本，不需要重启。文件改坏了（YAML 解析失败）时继续使用上一个能加载的版本，避免一处笔误放宽权限或中断服务。
- `WorkflowStore.revalidate()` 按当前策略复核所有记录了旧版本号的在途工作：
  - 待审批：新策略不再允许 → 标记 `invalidated`；新策略要求更多审批人 → 提高审批人数。
  - 已批准但还没开始执行：新策略不再允许 → 取消动作（`cancelled`），此时没有产生任何副作用。
  - 生效中的限时授权：角色被撤销 → 立即回收；最长时长缩短 → 到期时间按授权时间加新的最长时长提前。
- 只收紧、不放宽：审批人数只升不降，到期时间只提前不推后。放宽规则只影响新的申请。
- 有三处触发复核：worker 发现策略版本变化时（含启动时）自动扫一遍；审批人做决定时，如果单据的策略版本不是当前版本，先复核再计票；worker 每次执行尚未产生变更的动作前再检查一次（包括临时失败后的重试：版本扫描每个版本只跑一次，且只取消从未尝试过的动作，重试时必须自己挡住）。
- 每次处置都写审计（`policy_invalidated` / `policy_quorum_raised` / `policy_cancelled` / `policy_revoked` / `policy_shortened`），并计入指标 `it_copilot_policy_revalidations_total`。管理员可以调用 `POST /policy/revalidate` 立即复核。

## 后果

- 撤销一个角色后，最晚在下一次 worker 轮询时，旧的待审批单失效，已开通的权限进入回收。测试见 `tests/test_policy_revalidation.py`。
- 复核是幂等的，多个 worker 并发扫描也只会产生一次状态变化。
- 判断依据是版本号：只改规则内容、不升版本号，不会触发复核（新申请仍按新内容校验）。策略文件头部的注释要求改规则时必须升版本号。
- 代他人申请（`on_behalf_roles`）：审批记录保存申请人提交时的角色快照（`requester_roles`，不进冻结哈希）。新版本不再允许以该角色代申请时，待审批失效、未执行的动作取消、已生效的授权立即回收；申请人为本人申请的不受影响。快照之前创建的审批没有角色记录，不做推测，仍只复核动作本身。复核依据是提交时的角色，申请人之后在 IdP 中被降权不在范围内（需要目录同步）。
