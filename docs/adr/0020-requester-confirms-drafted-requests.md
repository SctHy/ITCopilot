# 0020 申请人确认 Agent 起草的申请后才进入审批

日期：2026-11-12 · 状态：已采纳

## 背景

模型调用写工具后，申请立即冻结并进入审批人队列。人工确认只有审批人这一道：参数是模型选的，选错设备、角色或时长时，申请人只能事后撤回（ADR 0017），或者再说一遍让新申请替代旧的（ADR 0007）。审批人则要先看完一份申请人本人都不会认可的单子再拒绝。

审批人确认的是“这件事该不该做”，申请人确认的是“这是不是我要的”，两件事不能互相替代。

## 决定

- 新增审批状态 `draft`：`draft → pending | expired | superseded | invalidated | withdrawn`。哪些操作需要确认由策略决定（`requester_confirmation`，默认是权限申请、密码重置、账号解锁和设备锁定；建单不需要）。草稿的有效期是 `confirmation_ttl_hours`（默认 24 小时）。
- 草稿和待审批单一样冻结并计算哈希，审计写 `created`（`awaiting_confirmation: true`）。草稿只有申请人本人看得到：审批人的列表和详情里都没有，管理员和审计员看得到。共享事项房间里成员能看到草稿卡片，但不能投票。对草稿投票返回 409。
- 确认：
  - **卡片**：`POST /approvals/{id}/confirm`，带上卡片上的 `payload_hash`。
  - **对话**：本会话有草稿时，回复“确认”“取消”这类短句由代码直接处理，不调用模型，因为确认与否是申请人的决定，交给模型只会再起草一遍。没有草稿时，同样的话照常交给 Agent。飞书走同一条路径。
- 确认和投票共用版本号 CAS：
  - 策略版本变了就先复核；
  - 确认时重新计算审批有效期；
  - 写审计 `confirmed`（`via: card | message`）；
  - 替代本会话里被它覆盖的旧待审批单。
  
  新草稿只替代旧草稿，不替代仍在待审批的单，所以申请人放着草稿不确认，不会丢掉已经提交的申请。
- 取消草稿复用撤回接口：结果是 `withdrawn`，审计里带 `draft: true`。草稿过期或被取消都不发通知，因为只有申请人见过它。
- 只有能把申请展示回申请人的调用方（对话、飞书、共享事项）会传入 `ask_requester=True`；`WorkflowStore.create` 的默认行为不变。

## 后果

- 走 Agent 的高风险变更都要两次人工确认（申请人一次，审批人一次）。代价是员工多一次点击或多回一句话。
- 确认是申请人对自己申请的认可，不是安全边界：越权仍然由身份、策略和职责分离拦截（ADR 0001）。草稿只是在审批人看到之前拦下“模型理解错了”。
- `approval_required` 仍表示“生成了审批记录”；新增的 `awaiting_confirmation` 表示它还是草稿。SSE 对应新增 `confirmation_required` 事件。
- 测试：`tests/test_requester_confirmation.py`；安全回归新增 `confirm_draft_only_by_requester`。
