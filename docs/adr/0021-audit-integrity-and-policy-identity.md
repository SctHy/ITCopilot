# 0021 审计完整性：来源摘要、管理操作先写意图、审计表只追加、策略按内容识别

日期：2026-11-12 · 状态：已采纳（修订 ADR 0008 中“判断依据是版本号”一条）

## 背景

复盘意图识别、工具授权、人工确认、审计与回滚的分层时，发现审计这一层有四个缺口：

1. 审批记录只保存原话前 500 字。模型为什么提出这个申请（意图层允许了什么、看到了哪些知识库片段、工具参数原样是什么），只在 Redis 的 trace 里，有 TTL。事后查“这个申请是不是被某篇 SOP 注入引导的”，到时候已经查不到。
2. 管理操作在成功之后另开事务写 `admin_audit`。进程在两步之间崩溃，修改已经生效，审计却没有记录。
3. “只追加”只是应用层的约定，数据库账号可以 UPDATE 或 DELETE 审计表。
4. 复核以策略版本号为准。只改规则、忘了升版本号时，待审批和已排队的旧申请不会复核，会按旧规则执行。策略文件本身被修改也没有任何审计。

## 决定

- **来源摘要**：创建审批时把本轮的来源写进不可变的 `created` 审计条目（`detail.provenance`），包括：
  - 意图、来源与置信度，以及意图层允许的写操作；
  - 预取和检索到的知识库引用；
  - 本轮每次工具调用的原始参数（凭据已脱敏）及结果；
  - request_id、trace_id、渠道。
  
  它不进冻结哈希，也不出现在审批详情里：审批人决定的是冻结的动作，不是解释。共享事项同样记录。
- **管理操作先写意图**：`api.deps.admin_change` 在修改前追加 `started`，结束后追加 `succeeded` 或 `failed`（`ref` 指回 `started`）。`started` 写不进去时修改不执行。查询默认列出成功的修改，以及超过 5 分钟仍无结果的 `interrupted`（可能已部分生效，需要核对）；失败的尝试保留，用 `outcome=failed` 查看。原来“失败的操作不出现在列表里”的语义不变。
- **只追加由数据库保证**：迁移 0002 给 `audit` 与 `admin_audit` 加触发器，拒绝 UPDATE、DELETE（PostgreSQL 另拒绝 TRUNCATE）。触发器挡得住应用缺陷和随手修改，挡不住数据库属主删除触发器；生产环境还应让应用账号对这两张表只有 INSERT 和 SELECT 权限。
- **策略按内容识别**：生效版本是 `声明版本号 + 规则指纹`（解析后规则的 sha256 前 12 位，注释和键顺序不影响）。所有冻结、比较、复核都用这个字符串，所以只改规则也一定会复核在途工作。worker 首次看到一个新的生效版本时写一条全局审计 `policy_loaded`（租户 `*`，各租户的管理员和审计员都看得到），内容包括声明版本、指纹、上一版本和复核结果。文件没有作者，修改人仍要看版本控制。
- **写操作清单只有一份**：`workflow/actions.py` 列出写操作的名称、意图说明、必填参数、风险等级和是否可补偿。工具注册、审批识别、策略必填校验、意图问题、saga 是否需要人工复核都从这里推导。工具注册和清单不一致时进程拒绝启动。

## 后果

- 审批列表和审批卡片显示的策略版本变长（例如 `2026-11-12.2+3f9c…`）；`approvals.policy_version` 加宽到 80。
- 升级后，旧版本号（不带指纹）的在途审批会被复核一次：仍被允许的照常推进。
