# 0018 按身份限流与数据保留清理

日期：2026-11-12 · 状态：已采纳

## 背景

每次对话都会调用模型，一个身份连续发请求就能占满模型额度和 worker（威胁模型原写“速率限制未实现，应在网关层处理”）。网关只看得到 IP 或令牌，看不到“这一请求会不会启动模型”，也覆盖不到飞书入口。另一方面，飞书收件箱、发件箱与情景记忆保存员工原话，从未清理，个人信息无限期留存（设计取舍表中“数据保留与删除策略”一栏）。

## 决定

**限流**（`core/rate_limit.py`）

- 只限“会启动模型工作”的入口，并共用一个预算 `agent_turn`：`/chat`、`/chat/stream`、要求 Agent 回复的事项消息、飞书消息。纯讨论、审批、查询不限。
- 按 `Principal.scope_key`（租户＋用户）计数，身份先校验再限流，未认证请求仍是 401。
- 算法用 GCRA：每个键只存一个时间戳；空闲的身份可以一次用完整个突发额度，之后按周期均匀放行；被拒绝的请求不消耗额度，重试不会让等待更久。
- Redis 上用一段 Lua 脚本原子执行，时间取 Redis 的 `TIME`，多个 API 进程共享同一预算，不依赖各进程时钟。没有 Redis 时退回进程内实现。
- HTTP 返回 429 和 `Retry-After`；飞书消息改为回复一句“消息太频繁”，不排队模型工作。
- Redis 出错时放行（fail open）：限流保护的是容量与费用，会话锁、幂等和审批另有保护；因为限流故障拒绝所有人是更大的事故。
- 默认 30 次/60 秒，`IT_COPILOT_RATE_LIMIT_AGENT_TURN` 可改或关闭；评测框架关闭限流（评测用同一演示用户连续回放）。

**数据保留**（`core/retention.py`）

- 清理：处理完（`done`/`ignored`）的飞书收件箱、已发出或已丢弃的发件箱，默认保留 30 天；情景记忆默认 90 天。0 表示永久保留。
- 收件箱行如果产生的审批还没结束（待审批，或已批准但执行未完成/需人工复核），就保留：审批结果通知要靠它找到回复地址。
- 不清理：审批、投票、动作、授权台账与审计日志（谁改了什么的记录）；失败的收发记录（需要运维处理）；共享事项讨论（业务记录，有归档流程）；用户画像（原地合并，体积有界）。Redis 中的工作记忆、回执、trace 与事件流本来就有 TTL。
- API 进程内每小时清理一次（`IT_COPILOT_RETENTION_INTERVAL_S`），按 500 行一批删除，避免长时间持有写锁；管理员可 `POST /ops/retention/run` 立即执行。删除行数计入 `it_copilot_retention_deleted_total{kind}`。

## 后果

- 限流是每身份的公平性控制，不是租户级费用配额，也不防分布式攻击；入口层的 IP 限流与 WAF 仍需要。
- 同一 `client_request_id` 的重复提交也计数（重放本身不调用模型，但仍是一次请求）。
- 情景记忆过期后，跨会话召回只能看到保留期内的历史；需要更长记忆的部署调大天数。
- 审计日志按审批组织、永久保留；如需满足“被遗忘权”，要另行设计对审计中个人信息的脱敏，不在本决定范围内。
